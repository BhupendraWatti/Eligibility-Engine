## Problem Statement

The homepage shows one "Closing Soon" row of three cards and a five-tile "Upcoming Examination & Application Milestones" strip that mixes form dates and exam dates. A candidate cannot see at a glance which drives are about to open, which are closing, which are in the exam stage, and which have results out. The "Popular" chips under the search box (10th Pass, 12th Pass, ITI, Diploma...) send people to a free-text search that does not filter by qualification, so they look like filters but are not.

## Changes

1. Hero CTA "Browse Active Jobs (N)" becomes **"Browse Exams (N)"**, scrolls to `#exam-board`. N = drives shown across the board's three columns.
2. New **exam board** section replaces "Closing Soon Applications":
   - Three columns: **Upcoming** | **Closing soon** | **On-going exams**.
   - A full-width **Results** strip under the three columns.
3. Remove the "Popular:" chips under the homepage search.
4. Remove the "Upcoming Examination & Application Milestones" section and its `milestones` computation.

## Premises (agreed)

1. Buckets come from the existing lifecycle (`src/services/lifecycle.ts`), no new stored fields:
   - Upcoming = `NOT_STARTED` (published, forms not open yet). Sorted by soonest `applicationStart`.
   - Closing soon = `isActiveDrive` (open or closing). Sorted by soonest `applicationEnd` (existing `closing_asc`).
   - On-going exams = forms closed, exam pending: `APPLICATION_CLOSED` or `EXAM_SCHEDULED`. Sorted by soonest `examDate`, undated last.
   - Results = `resultStatus === 'DECLARED'` / `RESULT_DECLARED`, or an active `RESULT` / `SCORECARD` / `MERIT_LIST` link (same rule as `/results`).
2. Each column keeps the visitor's state first (`queryListing` + `inRelevanceOrder`), shows up to 4 items, and has a "See all" link: `/jobs?status=UPCOMING`, `/jobs?status=OPEN`, `/jobs?status=CONCLUDED`, `/results`.
3. Removed sections are deleted, not hidden. The calendar link from the milestones header moves to the board header.
4. All-India scope: no state-specific copy.

## Approaches Considered

- **A: inline in `index.astro`** (chosen). Buckets computed in the page frontmatter, markup inline. Smallest diff.
- B: tested `src/services/home-board.ts` + `BoardColumn.astro`. Rejected by the user for now: more files for a homepage-only view.

## CEO review (2026-10-19, SELECTIVE EXPANSION)

Accepted additions:
- **CEO-D2 Countdown.** Each card shows a days-left line in IST: "Opens in N days" (Upcoming), "Closes today / tomorrow / in N days" (Closing soon), "Exam today / in N days" or "Exam date not announced" (On-going). Reuses `todayIST`.
- **CEO-D3 Admit / answer key flags.** On-going cards show "Admit card out" / "Answer key out" when the drive has an active `ADMIT_CARD` / `ANSWER_KEY` official link (same test as `admit-cards/index.astro:23-25`).
- **CEO-D4 Stale guard for On-going.** Show only if `examDate >= today` (IST), or no exam date and `applicationEnd` within the last 120 days. Dated exams soonest first, undated after. Drives marked `EXAM_COMPLETED` / `RESULT_DECLARED` never appear here.

Findings by section:
1. Architecture: one file, no new modules. Data = `loadPublicRecruitments(homeCode)` already loaded on the page; buckets are pure filters + `queryListing` for state tiers. OK.
2. Error & rescue: page already fails as a whole if D1 load fails (existing 500 page); `listing_load_degraded` covers home/central partial loads. Each bucket has its own empty state. No new failure path.
3. Security: no new input, endpoint or write. Removing chips removes links only. No issues found.
4. Data edge cases: missing dates render "Date not announced"; `totalVacancies` null renders "Refer notice"; long titles clamp to 2 lines. Stale drives handled by CEO-D4. Results: newest result date first (`importantDates` RESULT), undated after, max 4.
5. Code quality: bucket rules are inline (office-hours decision, untested; marked with a `gstack-shortcut` comment).
6. Tests: no unit tests by choice; `npm run check` (typecheck + build) and browser check at 375 / 768 / 1280 px.
7. Performance: four extra passes over at most a few hundred in-memory rows. No new queries. OK.
8. Observability: nothing new to log; read-only view.
9. Deploy: no migration, no flag. Rollback = revert the commit and redeploy (~5 min).
10. Trajectory: reversibility 5/5. If `/jobs` or the calendar need the same buckets, lift them into `src/services/` with tests (the shortcut trigger).
11. Design/UX: first view = hero, then the board. Every column needs an empty state. Mobile and tablet layout go to /design-consultation.

NOT in scope: personalised board from the eligibility profile; migrating `/results` to the Public Listing (already in TODOS.md).
