# Design: Viewer home-state detection and relevance-ordered listings

Generated by /office-hours on 2026-10-07
Branch: master
Repo: BhupendraWatti/Eligibility-Engine
Status: APPROVED
Mode: Startup

## Problem Statement

NIRNAY lists recruitments for Central + 28 states + 8 UTs on one feed. A UP aspirant opening the site sees MP, Bihar and Rajasthan posts mixed with their own and has to dig. We want the site to guess the visitor's state **without a browser location prompt**, show that state's posts first, and let anyone switch to another state in one tap. The open question was: after the home state, in what order should everything else appear?

## Demand Evidence

Founder hunch, pre-launch. No observed user behaviour yet. Consequence: the design must be cheap, reversible, and must never hide content when the guess is wrong.

## Status Quo

Aspirants use state-split "sarkari result" style portals and state-specific Telegram/WhatsApp groups. They already **pick a state explicitly**, so auto-detect only saves the first tap. What actually beats the status quo is a remembered state plus eligibility-aware ordering.

## Target User & Narrowest Wedge

The at-home graduate: lives in their domicile state, wants their state's posts and Central posts, and ignores other states. IP detection is usually right for this person. The migrant aspirant (e.g. a Bihar domicile coaching in Delhi) is the secondary user. Their IP guess is wrong by default, so a one-tap "Change", remembered after that, is mandatory.

Wedge: homepage + /jobs open on the visitor's state, with a visible "Showing for <State> · Change" control.

## Constraints

- All-India scope (CLAUDE.md). No MP defaults anywhere; `...Mp...` field names stay legacy-only.
- SSR on Cloudflare Workers (`output: 'server'`, `@astrojs/cloudflare` ^14.3). `Astro.request.cf.regionCode` is available in production, free on all plans, and needs no permission prompt. It is **undefined in `astro dev`** and in the dashboard preview.
- State-level IP accuracy is roughly 55-90%, and worse on mobile carrier NAT (Jio/Airtel gateways).
- ISO 3166-2:IN codes changed on 2023-11-23 (`OR→OD`, `CT→CG`, `TG→TS`, `UT→UK`) and on 2020-11-11 (`DN`/`DD`→`DH`). `src/data/india-jurisdictions.ts` uses `TG` and `DN`. Cloudflare's geo DB may return either old or new codes, so we need an alias map that accepts both.
- `src/middleware.ts` also enforces admin auth. New code must not change admin behaviour, and must skip `/admin` and the admin host entirely.
- No HTML response sets `Cache-Control` today (every page renders per request). Personalised pages must stay uncacheable at the edge (`Cache-Control: private` + `Vary: Cookie`) so a future cache rule can't serve UP ordering to an MP visitor.

## Premises (agreed)

1. The IP region is a **guess**, labelled as such ("Detected: Uttar Pradesh · Change"). It reorders; it never filters. Every state's posts remain reachable on the same page.
2. Signal priority: `?state=XX` in URL > `nirnay_state` cookie (set by the picker or the eligibility wizard) > `cf.regionCode` (only when `cf.country === 'IN'`, through the alias map) > none (national order, today's behaviour).
3. Relevance tiers, in order: **Home state → Central (`IN`) → other states open to all (`criteria.domicileStateCode` null) → other states domicile-locked**. The page's existing sort (closing soon, vacancies, recent) applies *within* each tier.
4. SEO-facing state views are driven by the URL (`/jobs?home=UP` tiers, `/jobs?state=UP` filters), never by IP. Googlebot (US IP) gets the national order on `/` and a deterministic page for any such URL.

> CEO review amendments (2026-10-07): premise 2's URL signal is `?home=XX` (renamed from `?state=` by D5). A URL `?home=` **shows** a state but never saves it (D4); only the picker (`remember=1`) and the wizard write the cookie.
5. Build only the cheap, reversible version now: no accounts, no analytics pipeline, no neighbour-state ranking.

## Approaches Considered

- **A: Homepage-only chip.** Rejected: logic would live in one page and get copy-pasted to /jobs, search, sectors.
- **C: Same HTML for all, reorder client-side.** Rejected: visible card jumps on slow phones and sort logic duplicated in JS. Revisit if HTML edge-caching becomes necessary.

## Recommended Approach: B, viewer-state resolver + relevance tiers

### Components

| Unit | Location | Responsibility |
|---|---|---|
| `resolveRegionAlias(code)` | `src/data/india-jurisdictions.ts` | Maps Cloudflare/ISO codes to NIRNAY codes: `TS→TG`, `DH→DN`, `DD→DN`, `OR→OD`, `CT→CG`, `UT→UK`, `UL→UK`. Returns `null` for unknown codes. |
| `resolveViewerState({url, cookies, cf})` | `src/services/viewer-state.ts` (new, pure) | Returns `{ code: string \| null, source: 'url' \| 'cookie' \| 'geo' \| 'none' }`. Validates every input against `INDIA_JURISDICTIONS` and rejects `IN` as a "home state". |
| Middleware hook | `src/middleware.ts` | For public (non-admin) requests only: `locals.viewerState = resolveViewerState(...)`. Sets the `nirnay_state` cookie **only** when `?home=XX&remember=1` is valid (1 year, `SameSite=Lax`, `Secure`, `Path=/`, not HttpOnly so the wizard can set it too). `?home=none&remember=1` saves the sentinel `none` (explicit national view; the resolver returns `{code:null, source:'cookie'}` and skips geo) (eng E1). A bare `?home=XX` (shared link) changes the view only (D4). |
| `listPublicRecruitments(request, deps)` | `src/services/public-listing.ts` (new) | Owns loading via injected `deps.load`: home-state + Central loads (`Promise.allSettled`, optional) in parallel with the national window (required); de-dupes by id; applies filters (incl. the real `state` filter, D5), sort, then tiers. If an optional load fails, still tiers the national window by the home code (D11, reopening D6) and logs `console.warn(JSON.stringify({event:'listing_load_degraded', which, stateCode}))` (D6). |
| `rankByRelevance(recs, homeCode)` | inside `src/services/public-listing.ts` (pure, exported for tests) | Returns `{ home, central, open, locked }`, each keeping input order (stable). With `homeCode` null it returns everything in one national bucket (today's behaviour). |
| `StatePicker.astro` | `src/components/common/` | Chip "Showing for <State> · Change" plus a native `<select>` of `INDIA_JURISDICTIONS` (excluding Central) and an "All India" option. GET form to the current path with `?home=` + hidden `remember=1`, so it works without JS and saves the choice. Label text varies by `source`: "Detected" for geo, nothing extra for url/cookie. |
| Wizard write-back | `src/components/eligibility/EligibilityWizard.tsx` | On submit, set the `nirnay_state` cookie from `domicileStateCode` (declared domicile beats geo), wrapped in try/catch like `Header.astro:193` so blocked cookies never break submit (S2-02). Pre-fill the domicile select from `viewerState.code` when it's empty. |

### CEO review additions (2026-10-07, all S effort)

- **Privacy (D7):** two sentences in `src/pages/privacy.astro`: an approximate state is inferred from the network per request and never stored; the `nirnay_state` cookie stores only a chosen state code.
- **Empty home tier (D8):** when the Home State has zero rows after filters, render "No current recruitments from <State>. Central and open-to-all posts below." in the home section, never a silent omission.
- **One "Open" rule (D9):** the Public Listing's status filter uses `src/services/lifecycle.ts` helpers only (`isActiveDrive`, `isUpcomingDrive`, `resolveRecruitmentLifecycle`). The legacy `lifecycleStatus` fallback from `jobs/index.astro:46` is dropped. Expected visible change: rows with a stale stored `OPEN` but a past `applicationEnd` leave the Open filter.
- **Override metric (D10):** when the middleware saves a state (`remember=1`), log `console.log(JSON.stringify({event:'viewer_state_saved', fromSource, fromCode, toCode}))` (state codes only, no IP). Read in Workers observability to measure how often the geo guess is wrong.

### Pages wired in v1

- `/` (index.astro): "Closing soon" and "Recently released" draw from `home` first, then fall back through the tiers. Show the chip above them.
- `/jobs`: the list is tiered by the resolved Viewer State (`?home=` overrides it for the view) with section headers ("Uttar Pradesh", "Central Government", "Other states — open to all", "Other states — domicile required"). The existing `sort` applies within each section. A new **State** dropdown in the filter bar sets `?state=XX` and filters to that jurisdiction only, like the existing org/qualification filters (D5).
- Later (not v1, see TODOS.md): `/search`, `/sectors/[sector]`, `/results`, `/admit-cards`, `/calendar` move to `listPublicRecruitments`.

### Architecture decisions (from /improve-codebase-architecture, 2026-10-07)

Today seven public pages (`index`, `jobs`, `search`, `sectors/[sector]`, `results`, `admit-cards`, `calendar`) each call `getAllActiveRecruitments()` and repeat text matching, status bucketing and sorting in their frontmatter. "Open" currently has three different definitions. Relevance tiers must not become an eighth copy.

1. **Public Listing module owns loading.** Pages describe a request (query text, filters, sort, Viewer State); the module returns tiered results. Loading goes through an injected loader, following the existing `RecruitmentQueryDeps.load` pattern in `recruitment-query.ts`. D1 and a test fake are two real adapters, so this is a real seam.
2. **Parallel targeted loads.** `getAllActiveRecruitments()` defaults to `limit: 100`, ordered by `isFeatured, createdAt` across all states and lifecycles, so at India-wide scale a state's older open posts fall out before any ranking runs. The module loads home-state rows (existing `stateId` option) + Central rows + the national window in parallel, then de-duplicates by id. Tiers `home` and `central` are never truncated.
3. **Shared predicates module (DEFERRED to TODOS.md by /plan-ceo-review HOLD-01).** v1 keeps the Public Listing's own text match and does not edit `recruitment-query.ts`. Target design when it lands: text match and state match move to a module imported by both the Public Listing and `recruitment-query.ts` (the MCP), so a website-only change can't alter MCP search (CLAUDE.md). Status classification is not re-implemented there: it calls `isActiveDrive` / `resolveRecruitmentLifecycle` from `src/services/lifecycle.ts`, the canonical authority. This removes the `|| lifecycleStatus === 'OPEN'` fallback in `jobs/index.astro`.
4. **Sector membership** (follow-up): the sector page's first-word title match (`sectors/[sector].astro:26-30`) disagrees with `calculateSectorActiveDrives` (`postId → sectorId`). Fold one membership rule into the Public Listing's sector filter.
5. **Middleware stays a dispatcher.** Viewer State resolution is a pure function called for public requests only. No adapter interface for the geo source: `request.cf` is the only real source, and tests pass a plain `{ country, regionCode }`.

Glossary terms (Home State, Viewer State, Relevance Tier, Public Listing, Domicile-locked) are recorded in `markdown/CONTEXT.md`.

### Data flow

```
request ─▶ middleware ─▶ resolveViewerState(url, cookie, cf)
                              │  url ?home   ─┐
                              │  cookie       ├─▶ first valid wins ─▶ locals.viewerState {code, source}
                              │  cf.regionCode┘   (via resolveRegionAlias, country=IN only)
                              └─ ?home=XX&remember=1 ─▶ Set-Cookie nirnay_state (only path that saves)
page ─▶ listPublicRecruitments({q, filters, state?, sort, viewerState})
          ├─ load national window (required) ─┐
          ├─ load home stateId   (optional)  ─┼─▶ allSettled ─▶ dedupe by id ─▶ filters ─▶ sort ─▶ rankByRelevance ─▶ tiers
          └─ load Central st_in  (optional)  ─┘        └─ optional rejected ─▶ warn listing_load_degraded, still tier the national window (D11)
```

## Open Questions

1. Should the chip say "Detected" at all, or just show the state name? "Detected" is honest, but it may also prompt privacy worries. Decide in /plan-design-review.
2. Central posts rank above other states for everyone. Is that right for at-home state aspirants who never sit central exams? (Default yes; revisit with real click data.)
3. Do the privacy policy and `/privacy` page need a line about IP-derived region and the preference cookie under India's DPDP Act? (Likely yes, one sentence.)
4. Should `/jobs?state=XX` become a canonical SEO page (`/states/uttar-pradesh`) later? Out of scope for v1. A candidate for /plan-ceo-review.

## Success Criteria

- A visitor whose `cf.regionCode` is `UP` sees UP posts first on `/` and `/jobs` with zero clicks.
- A visitor with a wrong guess fixes it in at most 2 taps, and the choice survives a return visit.
- Telangana (`TS`) and Dadra & Nagar Haveli and Daman & Diu (`DH`) visitors resolve correctly.
- `/admin` behaviour and response headers are byte-for-byte unchanged.
- Unit tests cover: alias map (all renamed codes), resolver priority order, invalid/`IN`/garbage inputs, and tiering stability.
- With no signal (local dev, Googlebot, non-India), output matches today's national order exactly.

## Dependencies

- None blocking. Uses existing `stateCode` and `criteria.domicileStateCode` on every recruitment.

Send each the live workers.dev link and ask one question: "Which state's jobs did you look for first, and how did you find them?" Write down what they actually did, not what they said they'd like. If 2 or more of them are migrants, swap the target user and make the picker more prominent than the geo guess.

## What I noticed about how you think

- You named the hard part yourself before I did: "but here is the catch what if the user wanted to see the job post of different state". Most people ship auto-detect and discover the override problem from angry users.
- You asked "how we are going to select which state we should show?" That question led to the eligibility-tier ordering, which is the part of this design no state-split portal can copy without NIRNAY's domicile data.
- You answered "personal hunch" on demand instead of inflating it. That honesty is why this design is reversible rather than a personalisation platform.
