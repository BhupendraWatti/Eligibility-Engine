## Problem Statement

Every recruitment needs one honest answer to "can a candidate from another state fill this form?". Today that answer is spread over three fields: `domicileStateCode`, `reservationStateCode` and the legacy `requiresMpDomicile`. The MCP is the main writer of those fields, and the current defaults make the wrong answer the easy one:

- An empty `domicileStateCode` is shown as **"Open All-India"** (`src/pages/jobs/index.astro:60-62`) and sorted into the "open" tier (`src/services/public-listing.ts:107-109`). The MCP's rule "leave out any field you are not sure of" therefore publishes the most consequential label by omission.
- `requiresMpDomicile: true` with no state code means "MP domiciles only" for a recruitment of any state (`src/engine/eligibility.ts:143-144`, `src/services/cadre-guide.ts:134-136`).
- `domicileStateCode` is validated as a free string (`src/services/change-proposals.ts:82`), so `TS` instead of `TG` locks out everyone.
- One recruitment can be locked to any state, not just its own.

## Demand Evidence

None observed yet. The site is live with few or no real users. This work protects trust before users arrive, not in response to complaints.

## Status Quo

Aspirants read the notice PDF themselves and hunt for the domicile clause. Many misread it, pay the fee and are rejected at document verification. A wrong label on NIRNAY reproduces that loss with NIRNAY's name on the advice, so a wrong label is worse than no label.

## Target User & Narrowest Wedge

The aspirant browsing other states' jobs (the "open" and "locked" relevance tiers). Wedge: the MCP cannot write a wrong "who can apply" label, and an unchecked recruitment says so instead of claiming "open".

## Constraints

- All-India scope (CLAUDE.md). No MP defaults. `...Mp...` names stay legacy-only.
- The MCP may only propose. Values go live through `src/services/change-proposal-decision.ts` after admin approval, and the admin only approves without re-checking, so validation must happen at proposal time.
- Article 16(2) bars residence-based discrimination in public jobs. Most state notices therefore do **not** bar outsiders; they reserve quotas, relaxations or local seats for domiciles, and outsiders compete as Unreserved. Outright "domiciles only" exists but is the minority.
- The word "domicile" in a notice usually refers to the certificate needed **to claim reservation**, not to an eligibility bar. A check that only looks for the state's name in the quote would pass the most common misreading.
- Proposal text must be English (`assertEnglish`, `src/services/change-proposals.ts:165-167`), but **evidence snippets stay verbatim**, so domicile quotes will often be Hindi or another regional script.
- Enum fields are never machine-checked today: `src/services/fact-checks.ts` reports them as `NEEDS_READING` for the admin. `VALUE_NOT_IN_QUOTE` applies only to numbers, dates and the advertisement number.

## Premises (agreed)

1. A wrong "who can apply" label is worse than no label. An unset value means **Not checked yet**, never "open".
2. There are three real answers plus unknown: `STATE_ONLY`, `OPEN`, `OPEN_STATE_QUOTA` (anyone may apply; category and women relaxations only for the recruitment state's domiciles), `UNKNOWN`. The MCP picks one explicitly, with a quote.
3. The word "domicile" in a quote is not proof of `STATE_ONLY`. The quote must be the eligibility clause itself.
4. A state recruitment can only be locked to its own state. A Central (`IN`) recruitment is never domicile-locked.
5. Partial local quotas ("80% of posts for local candidates") are out of scope. The MCP flags them to the admin in the proposal note instead of modelling them.

## Approaches Considered

- **A: Sentinel value in `domicile_state_code`** (NULL = not checked, `ALL` = open). Rejected: a magic string every reader of the domicile fields (19 files under `src/` today) must learn, and the quota case still needs two fields kept consistent by hand.
- **C: Show the quoted clause on the public page.** Not rejected; it stacks on B and is the natural follow-up (see Open Questions).

## Recommended Approach: B, one scope field with the state implied

### Scope semantics

`domicile_scope` is the single source of truth. The state it refers to is always the recruitment's own state (`recruitments.state_id`), never stored separately.

| Scope | Who may apply | Category / women relaxations | Public label |
|---|---|---|---|
| `STATE_ONLY` | domiciles of the recruitment state only | that state's domiciles | "{State} domiciles only" |
| `OPEN_STATE_QUOTA` | any Indian citizen | that state's domiciles; outsiders compete as Unreserved | "Open to all, quota for {State}" |
| `OPEN` | any Indian citizen | everyone, per the notice | "Open to all Indian citizens" |
| `UNKNOWN` | not checked | treated conservatively (see Engine) | "Domicile rule not checked, see notice" |

**Central (`IN`) recruitments are always `OPEN`.** Every writer forces `OPEN` for an `IN` recruitment on CREATE and on every approval or save, whatever the input says. The MCP may omit the field for Central; an explicit non-`OPEN` scope is refused. No reader treats a Central row as `UNKNOWN`.

**State changes.** The reset fires only when the recruitment's effective state code changes; an organisation correction within the same state keeps the scope. Moving to `IN` sets `OPEN`. Moving from `IN` to a state, or from one state to another, resets the scope to `UNKNOWN`: the old scope was evidence about a different jurisdiction's notice. When the same save or proposal also supplies a scope, the reset is applied first and the supplied scope is then validated against the new state (a non-`OPEN` value for `IN` is refused).

`recruitments.state_id` is `NOT NULL` with a foreign key to `states` (`migrations/0001_init.sql:81`), so every row has a state code to derive from.

### Data

Migration `0017_domicile_scope.sql`:

```sql
ALTER TABLE recruitment_eligibility ADD COLUMN domicile_scope TEXT NOT NULL DEFAULT 'UNKNOWN';

-- Central is never locked (premise 4).
UPDATE recruitment_eligibility SET domicile_scope = 'OPEN'
  WHERE recruitment_id IN (SELECT r.id FROM recruitments r JOIN states s ON s.id = r.state_id WHERE s.code = 'IN');

-- An explicit lock survives only when it names the recruitment's own state.
UPDATE recruitment_eligibility SET domicile_scope = 'STATE_ONLY'
  WHERE domicile_scope = 'UNKNOWN'
    AND recruitment_id IN (
      SELECT r.id FROM recruitments r JOIN states s ON s.id = r.state_id
      WHERE s.code <> 'IN'
        AND UPPER(COALESCE(recruitment_eligibility.domicile_state_code,
                           CASE WHEN recruitment_eligibility.requires_mp_domicile = 1 THEN 'MP' END)) = s.code);

-- Everything else stays UNKNOWN, including rows with only reservation_state_code set and
-- locks that name another state: none of them is evidence about who may apply.

-- Backfill the legacy columns from scope so readers behave correctly before any row is re-saved
-- (same rules as deriveDomicileColumns below).
UPDATE recruitment_eligibility SET domicile_state_code = NULL, requires_mp_domicile = 0
  WHERE domicile_scope <> 'STATE_ONLY';
UPDATE recruitment_eligibility SET domicile_state_code = (SELECT s.code FROM recruitments r JOIN states s ON s.id = r.state_id WHERE r.id = recruitment_eligibility.recruitment_id),
                                   reservation_state_code = (SELECT s.code FROM recruitments r JOIN states s ON s.id = r.state_id WHERE r.id = recruitment_eligibility.recruitment_id)
  WHERE domicile_scope = 'STATE_ONLY';
UPDATE recruitment_eligibility SET requires_mp_domicile = CASE WHEN domicile_state_code = 'MP' THEN 1 ELSE 0 END
  WHERE domicile_scope = 'STATE_ONLY';
UPDATE recruitment_eligibility SET reservation_state_code = NULL
  WHERE domicile_scope = 'OPEN';
-- UNKNOWN state rows: relaxations only for the recruitment's own state (conservative).
UPDATE recruitment_eligibility SET reservation_state_code = (SELECT s.code FROM recruitments r JOIN states s ON s.id = r.state_id WHERE r.id = recruitment_eligibility.recruitment_id)
  WHERE domicile_scope = 'UNKNOWN';
```

After the migration a check query must return 0 rows where the stored legacy columns differ from `deriveDomicileColumns(scope, state)`: `domicile_state_code`, `reservation_state_code` and `requires_mp_domicile` together.

Before running it remotely, a read-only query lists the rows that fall back to `UNKNOWN` despite having a domicile code, the MP flag or a reservation code (code naming another state, MP flag on a non-MP row, Central with a code). Their count and ids go into the re-check run's worklist.

The legacy columns stay and are **derived** from scope by one pure function. Old readers keep working, and the legacy columns are never written any other way:

```ts
// src/services/domicile-scope.ts (new, pure)
export const DOMICILE_SCOPES = ['UNKNOWN', 'STATE_ONLY', 'OPEN', 'OPEN_STATE_QUOTA'] as const;
export function deriveDomicileColumns(scope: DomicileScope, stateCode: string) {
  // stateCode 'IN'    -> scope is forced to OPEN by the caller first; returns the OPEN row
  // STATE_ONLY        -> domicileStateCode = state, reservationStateCode = state, requiresMpDomicile = (state === 'MP')
  // OPEN_STATE_QUOTA  -> domicileStateCode = null,  reservationStateCode = state, requiresMpDomicile = false
  // OPEN              -> domicileStateCode = null,  reservationStateCode = null,  requiresMpDomicile = false
  // UNKNOWN           -> domicileStateCode = null,  reservationStateCode = state, requiresMpDomicile = false
}
```

`UNKNOWN` keeps relaxations conservative: outsiders never get category or women relaxations on an unchecked state recruitment, and home-state candidates keep theirs. A stored reservation code naming another state is never reused. A companion `normaliseScope(scope, stateCode)` returns `OPEN` for `IN` and is the only way writers obtain the scope they store, so `deriveDomicileColumns` never sees an invalid pair.

### Writers (every path that stores eligibility)

Every save ends in one of three `src/db/queries.ts` writers: `createRecruitmentAtomic`, `updateRecruitmentAtomic` and `updateRecruitmentEligibility`. **Derivation lives only there** (eng review D1): each resolves the recruitment's state code, applies `normaliseScope` and the state-change rule, and writes the legacy columns from `deriveDomicileColumns`. No caller computes legacy columns, and callers that pass them have them ignored.

| Caller | Change |
|---|---|

| `src/db/queries.ts` writers (`domicileStateCode` writes at ~3585, 3665, 3989, 4089, 4119, 4299) | Take `domicileScope`; an update with `domicileScope` undefined keeps the stored value; derive. Duplicate copies the scope. |
| `src/pages/admin/recruitments/new.astro`, `[id]/edit.astro` | Four-option scope picker replaces the checkbox and state select, **in the same change**. |

### MCP surface (`src/services/change-proposals.ts`)

- Add `domicileScope: { enum: ['STATE_ONLY', 'OPEN', 'OPEN_STATE_QUOTA'] }` to `EDITABLE_FIELDS`. Leaving it out means "unchanged" on UPDATE and `UNKNOWN` on CREATE (`OPEN` for Central).
- Remove `requiresMpDomicile`, `domicileStateCode` and `reservationStateCode` from `EDITABLE_FIELDS`. The MCP never types a state code again.
- Refuse `STATE_ONLY` or `OPEN_STATE_QUOTA` on a Central recruitment with a new block code `DOMICILE_SCOPE_INVALID`. `OPEN` on Central is dropped before validation (no evidence or clause check), since the value is forced anyway.
- MCP docs state plainly: a state recruitment whose notice is silent about other-state candidates stays `UNKNOWN`; do not send `OPEN` on the strength of the citizenship clause.
- `domicileScope` needs evidence through the generic `EVIDENCE_REQUIRED` rule (it is not in `EVIDENCE_EXEMPT_FIELDS`). As an enum it never reaches `VALUE_NOT_IN_QUOTE`; it is validated only by the clause check below.
- Reverting a wrong scope to `UNKNOWN` is admin-only, via the scope picker.
- Update `src/services/reference-data.ts` and `mcp/src/server.ts` to explain the three values, with one real example sentence each, including the quota-with-"only" trap.

### Clause check for `domicileScope`

A new pure function in `src/services/fact-checks.ts`, `classifyDomicileClause(snippet, stateName)`, returns `STATE_ONLY`, `OPEN_STATE_QUOTA`, `OPEN` or `UNCLEAR`.

**It ships in refuse mode.** A `domicileScope` proposal is accepted only when its quote classifies as exactly that scope. A different scope **or `UNCLEAR`** is refused with `DOMICILE_CLAUSE_MISMATCH`, and the message tells the MCP to quote the eligibility clause or leave the field out (so the row stays "Not checked yet"). There is no flag-only mode, because the admin does not re-read. A clause the classifier cannot read (another script, unusual wording) costs a "Not checked yet" label, never a wrong one.

Signals are matched within one sentence. Sentences split on `.`, `?`, the Hindi danda `।` and line breaks, never on `;` or `,` (the required fixtures pin this).

**Exclusions are checked first.** A sentence containing a certificate term ("certificate", "प्रमाण पत्र") or using a residence word for something other than the candidate ("native language", "local language", "स्थानीय भाषा") never counts as a lock phrase, whatever else it contains.

- **Outsider phrase**: a reference to candidates from other states: "candidates of other states", "outside the state", "other than domiciles", "अन्य राज्य", "अन्य राज्यों के". Bare "unreserved" or "general category" never counts.
- **Benefit phrase**: "reservation", "relaxation", "benefit of", "आरक्षण", "छूट".
- **Lock phrase**: a bar plus a residence term in the same sentence: "only" / "shall not be eligible" / "not eligible" / "केवल" / "पात्र नहीं" **with** "domicile" / "resident" / "bona fide" / "native" / "मूल निवासी" / "निवासी", or "candidates of other states ... not eligible". Generic ineligibility ("candidates in State service shall not be eligible") has no residence term and never counts.
- **State reference**: the state's name or alias, or "the State" / "this State" / "राज्य" (accepted because the source is the recruitment's own notice).
- **Open phrase**: wording about candidates from other states, not nationality: "candidates of any state", "candidates from other states may also apply", "domicile is not required", "all India basis", "सभी राज्यों के अभ्यर्थी". The citizenship clause ("must be a citizen of India", "भारत का नागरिक") appears in nearly every notice, including locked ones, and never counts.

Classification:

1. Lock phrase + state reference, and **no** sentence with outsider + benefit phrases -> `STATE_ONLY`.
2. A sentence with outsider + benefit phrases ("candidates of other states will be treated as Unreserved and get no reservation benefit"), and no lock phrase -> `OPEN_STATE_QUOTA`. *"Reservation is only for domiciles of Madhya Pradesh; candidates of other states will be treated as Unreserved"* lands here: its "only" sentence has a residence term, but the clause also has an outsider + benefit sentence, so rule 1 does not apply, and rule 2 does because "only ... domiciles" here bars a benefit, not eligibility. To keep that distinction mechanical, a lock phrase whose sentence also contains a benefit phrase is not a lock phrase.
3. Open phrase, with no lock phrase and no outsider + benefit sentence -> `OPEN`.
4. Both a lock phrase and an outsider + benefit sentence, or none of the above (including certificate-only wording: "domicile certificate", "to claim reservation", "मूल निवास प्रमाण पत्र") -> `UNCLEAR`.

Phrase lists live in one exported constant shared by tests and MCP docs. Latin and Devanagari ship first; other scripts classify as `UNCLEAR` (refused, row stays "Not checked yet") until a fixture from that script justifies a list. Whether obligation wording ("must be a domicile of Rajasthan", "should be a bona fide resident of the State", "होना चाहिए") counts as a lock phrase is decided from the Assignment's real clauses; until then it classifies as `UNCLEAR` (fails safe). Required test fixtures: "Only domicile certificates issued by the competent authority of the State will be accepted" (not `STATE_ONLY`), a native-language requirement (not `STATE_ONLY`), "Candidate must be a citizen of India" alone (`UNCLEAR`), an obligation-wording lock clause, the quota-with-"only" sentence (`OPEN_STATE_QUOTA`), a lock clause quoted together with its SC/ST/OBC relaxation sentence (`STATE_ONLY`), a certificate-only sentence (`UNCLEAR`), a non-domicile "shall not be eligible" sentence (not `STATE_ONLY`), a Hindi lock clause, a "this State" clause, plus the Assignment's five real clauses.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: MAX_ITERATIONS

### R3-1 — feasibility (blocking)

**Problem**

> The new lock phrase is any bar word ('only', 'not eligible', 'केवल') plus any residence term in the same sentence. Two very common non-eligibility sentences match it. The first is certificate wording: 'Only domicile certificates issued by the competent authority of the State will be accepted.' The second is language wording: 'Only candidates who can read and write the native language of the State ...'. Both have 'only' plus a residence term ('domicile', 'native') plus a state reference ('the State'), and neither has a benefit phrase. Rule 1 fires before rule 4's certificate-only exclusion is reached, so both classify as STATE_ONLY. A wrong STATE_ONLY proposal backed by the certificate sentence (the 'most common misreading' named in the Constraints) is then accepted and goes live as '{State} domiciles only'.

**Remedy**

> A sentence that contains a certificate term ('certificate', 'प्रमाण पत्र') or uses the residence word only as an adjective of something other than the candidate (for example 'native language') is not a lock phrase. Make rule 4's certificate-only exclusion take precedence over rule 1. Add negative fixtures for 'Only domicile certificates issued by ... the State will be accepted' and for a native-language requirement, both expected to classify as not STATE_ONLY.

### R3-2 — feasibility (blocking)

**Problem**

> 'Candidate must be a citizen of India' is the nationality clause in almost every notice, including state notices that also carry a domicile lock in a different sentence. Rule 3 classifies a quote of only that sentence as OPEN. The MCP can therefore back an OPEN proposal on a locked recruitment with the nationality clause, and it is accepted in refuse mode. The result is 'Open to all Indian citizens' on a domiciles-only recruitment, which is the most harmful wrong label under premise 1. Refuse mode cannot see the rest of the notice, so citizenship wording is not evidence about other-state candidates.

**Remedy**

> Do not count citizenship alone as an open phrase. OPEN should need wording that addresses candidates from other states ('candidates of any state', 'all India', 'domicile is not required', 'candidates from other states may also apply'). A citizenship-only quote should classify as UNCLEAR, so the row stays 'Not checked yet'. Add the citizenship-only sentence as a fixture expected to return UNCLEAR, and state in the MCP docs that state recruitments whose notice is silent stay UNKNOWN.

### R3-3 — completeness (blocking)

**Problem**

> Read literally, this writer row resets the scope to UNKNOWN on any change to the organisation, even when the state stays the same. A routine organisation correction would then wipe a verified scope. The design also does not say what happens when one admin save or one MCP UPDATE changes the state and supplies a new domicileScope in the same request: the reset could discard the scope that was just validated.

**Remedy**

> Reset only when the recruitment's effective state code actually changes; an organisation change within the same state keeps the scope. When the same save or proposal also supplies a scope, apply the reset first and then the supplied scope, validated against the new state (refuse a non-OPEN value when the new state is IN).

### R3-4 — consistency (minor)

**Problem**

> This line says an OPEN scope on a Central recruitment is accepted as a no-op. But the clause-check section says every domicileScope proposal is accepted only when its quote classifies as exactly that scope, and EVIDENCE_REQUIRED applies to the field. An OPEN on Central sent with no quote, or with a quote that classifies as UNCLEAR, is therefore refused under one rule and accepted under the other.

**Remedy**

> Say that for Central recruitments the evidence requirement and the clause check are skipped for domicileScope (or that the value is dropped before validation), because the value is forced to OPEN anyway.

### R3-5 — clarity (minor)

**Problem**

> The classifier now depends on sentence boundaries, but the design does not define them. The required quota-with-'only' fixture uses a semicolon. If ';' splits sentences, the second half ('candidates of other states will be treated as Unreserved') has no benefit phrase, so the clause classifies as UNCLEAR instead of OPEN_STATE_QUOTA. The Hindi danda '।' and numbered sub-clauses are also not addressed.

**Remedy**

> Define the sentence delimiters: for example '.', '।', '?' and line breaks, but not ';' or ','. Note that the required fixtures pin this choice.

### R3-6 — consistency (minor)

**Problem**

> The backfill says it follows deriveDomicileColumns, but for STATE_ONLY rows it never sets requires_mp_domicile. An MP row locked through domicile_state_code = 'MP' with the flag at 0 keeps 0, although the derive function returns true. A non-MP row locked through its own state code with a stray MP flag at 1 keeps 1. Old readers that still use the flag can then disagree with the scope.

**Remedy**

> Add requires_mp_domicile = (state code = 'MP') to the STATE_ONLY backfill UPDATE. Extend the post-migration check to cover domicile_state_code and requires_mp_domicile.

### R3-7 — completeness (minor)

**Problem**

> deriveDomicileColumns and the migration subqueries assume that every recruitment has a state. The design does not say what happens to a recruitment with a NULL state_id, or with a state that is missing from the states table. The backfill would leave reservation_state_code NULL there, and the derive call has no stateCode to use.

**Remedy**

> State whether recruitments.state_id is guaranteed NOT NULL. If it is not, define the scope and legacy columns for state-less rows (for example UNKNOWN with reservation_state_code NULL, plus a publication-validator block) and exclude them explicitly from the check query.

### R3-8 — completeness (minor)

**Problem**

> Real lock clauses are often written as obligations rather than bars ('The candidate must be a domicile of Rajasthan', 'should be a bona fide resident of the State'). These have no 'only' or 'not eligible' word, so they classify as UNCLEAR and are refused. This fails safe, but it may leave many genuinely locked recruitments as 'Not checked yet' after the re-check run.

**Remedy**
